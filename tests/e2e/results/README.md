# RAST E2E results — method and raw data

Everything in this directory is produced by the harness in `tests/e2e/` against
the disposable dev instance from `scripts/e2e/dev-instance.sh`. The production
instance on `127.0.0.1:8720` is only a reference for the legacy behaviour and is
never touched.

## Layout

| File | Content |
|---|---|
| `<mode>-latest.json`, `<mode>-latest.md` | Last scenario run (`docker` or `native`): 14 scenarios (s0, a–m), pass/fail matrix, evidence, details, metrics. |
| `<mode>-<timestamp>/results.json`, `matrix.md` | Immutable copy of each run. |
| `perf-<mode>-latest.json`, `perf-<mode>-latest.md` | Performance measurements for one backend. |
| `perf-docker-latest.json`, `perf-native-latest.json` | Inputs of the comparison. |
| `perf-comparison.md` | Docker-vs-native table (generated by `--compare`). |
| `../screenshots/<mode>/<scenario>/` | Screenshot evidence per scenario. |
| `../perf/raw/`, `../tmp/` | Scratch data (git-ignored). |

## Environment

* One dev instance at a time per backend profile: `127.0.0.1:8731` (docker) and
  `127.0.0.1:8732` (native). Each has its own data/config/credentials under
  `/tmp/rast-e2e` and `/tmp/rast-native-e2e`; the harness selects the instance
  with `--instance-root`.
* **Only one native-mode RAST instance may exist per host** — systemd transient
  units (`rast-xpra-u<userId>`, `rast-app-u<uid>-…`) are host-global and each
  native server's recovery stops units it does not know. Docker-mode instances
  do not conflict.
* Host: same machine for both backends, loopback browser (no WAN), same
  fixtures (`tests/e2e/fixtures/`), same test accounts, Chrome 157.0.8103.78.
* Host load is recorded implicitly by outliers; measurements were taken while
  other agent builds/tests ran, so absolute values are conservative and the
  Docker-vs-native comparison is on the same host at the same period.

## Scenario method (runner: `node tests/e2e/run.mjs --mode=<backend> --scenario=…`)

* Every scenario starts from the real login form or a real API session, drives
  the actual desktop UI in headless Chromium (Playwright 1.55), and asserts on
  both the DOM (`.window[data-window-id]`, `.win-title`, `.taskbar-app`) and the
  backend API/session state. Host-level facts (Docker copies, `rast-xpra-*`
  systemd units, cgroups, dpkg) are read with `sudo` via `lib/host.mjs`.
* Screenshots are captured at each milestone; on failure the run keeps the
  screenshot set and the error in the matrix.
* Scenario prerequisites are idempotent: a scenario installs the app it needs
  if it is missing (upload through File Station API → App Center install job).

## Performance method (`node tests/e2e/perf/run-perf.mjs --mode=<backend> --instance-root=…`)

All timestamps are milliseconds, taken in the Node process with `Date.now()`;
the browser and server are on the same host, so network transit is negligible.

| Measurement | Start | End |
|---|---|---|
| **Cold launch** | click on the app tile in the desktop start menu, with no session/copy for that user (session unit stopped / Docker copies removed and verified) | first pixel change of the app window's screenshot after the RAST window appeared (window visible + content painted) |
| **Warm launch** | same click, but the session/copy already exists (app previously opened and its windows closed; the backend session stays alive) | as cold |
| **time-to-first-pixel** | the RAST window appeared in the DOM | first changed pixel of that window |
| **launch API response** | HTTP POST `/api/linux-apps/{id}/open` or `/launch` | response received |
| **backend session ready** | the same POST | the session reports `ready` and the run/copy reports running (polled every 200 ms) |
| **identity provisioning** (native only) | first-ever launch for a user | session ready; includes `useradd`/`groupadd`/home setup (8–17 s on this host). Reported separately so cold launch without identities is not conflated. |
| **idle memory** | 60 s after the last input with the app open | native: `systemctl show rast-xpra-u<id>.service -p MemoryCurrent,MemoryPeak` and `memory.current`/`memory.peak` of the session cgroup plus every app unit cgroup; Docker: `docker stats --no-stream` memory of the user's copy containers |
| **active CPU** | start of a scripted 8 s interaction (typing into the app + scrolling) | native: delta of `cpu.stat usage_usec` of the session + app cgroups over the interval; Docker: average of `docker stats` CPU% sampled during the same interval |
| **input latency** | `Date.now()` immediately before `keyboard.press` / mouse click into the streamed window | first changed pixel of the window screenshot (20 ms polling). Includes Playwright/Chromium and screen-encoding overhead → documented as an upper bound |
| **two-user case** | both users launch Chrome concurrently through the API | both sessions/copies `ready`; combined memory from both users' cgroups/containers; CPU sampled during simultaneous interaction |

"Cgroups": native units run in `rast-linux.slice`, so their files are read from
`/sys/fs/cgroup/rast.slice/rast-linux.slice/<unit>/` (resolved from
`systemctl show <unit> -p ControlGroup`), not `system.slice`.

## Quick backend variant (`perf/quick-perf.mjs`)

For a fast, comparable baseline it drives the backend directly instead of the
desktop shell: launches go through `POST /api/linux-apps/{id}/open` (docker) or
`/launch` (native), and typing/scrolling are sent to the streamed page
(`/linux-apps/<key>/` or `/linux-apps/session/<key>/`) opened directly in
Chromium. This removes the window-manager UI from the measurement and makes
docker/native numbers directly comparable.

* cold launch — no copy/session for the user → backend reports ready (stream URL
  available) and the streamed page paints its first frame;
* warm launch — same, with the session/copy already running (session retained
  is asserted);
* idle memory — cgroup `memory.current` of the user's container(s) (docker:
  `/sys/fs/cgroup/system.slice/docker-<id>.scope`) or systemd unit cgroups
  (native: `rast-xpra-u<id>` + app units) after 60 s without input;
* active CPU — `cpu.stat usage_usec` delta computed over the same scripted 10 s
  typing+scrolling interaction for both backends (no `docker stats` sampling
  bias), memory sampled during the interaction;
* input — one keypress to first changed streamed page pixel;
* two-user — both users' Chrome launched concurrently, combined memory from
  both cgroups and CPU during simultaneous interaction, plus time until both
  are ready.

Raw files: `perf-quick-docker-latest.json`, `perf-quick-docker-latest.md`;
native output is `perf-quick-native-latest.*` once the native app-window
blocker (see `native-blockers-2026-11-12.md`) is fixed.

## Known limits and explicitly not measured

* **GPU/encoder utilisation and FPS** are not exposed by either backend; Xpra
  encoder/encoding selection is read from the Xpra log when present, with no
  per-frame statistics.
* **WAN/network latency** is not measured (loopback browser on the same host;
  production traffic passes Cloudflare/nginx).
* **Screen capture overhead inside the browser** means input latency is an upper
  bound, not an app-side number.
* **Docker image build time** is an installation metric (scenario a), not a
  launch metric. The Docker base image (`rast-linux-base:<hash>`) is shared and
  cached; the first app build is much slower than later ones and is reported as
  "cold install".
* **Host load** from concurrent CI/agent work on the shared host can inflate the
  first minutes of a run; the raw JSON keeps every sample so outliers are
  visible rather than hidden behind a mean.
* **One native instance per host**: native scenarios cannot run while another
  native-mode RAST instance is running (unit-name collision, see above).
* **Idle cleanup timings** differ by design: Docker stops a copy 60 s after its
  last window (EMPTY_GRACE) or after 30 min without input; native uses
  `linux_idle_minutes` (2 min in the E2E config) and stops the whole shared
  session when nothing is left running.

## Reproduce

```bash
# fixtures (GTK3 test app + portable archive + invalid debs/archives)
tests/e2e/fixtures/build-fixtures.sh

# docker baseline
scripts/e2e/build-snapshot.sh
scripts/e2e/dev-instance.sh up docker
cd tests/e2e && npm install
node run.mjs --mode=docker --scenario=all
node perf/run-perf.mjs --mode=docker --instance-root=/tmp/rast-e2e

# native backend (stop any other native instance first!)
scripts/e2e/build-snapshot.sh
RAST_E2E_ROOT=/tmp/rast-native-e2e RAST_E2E_BIND=127.0.0.1:8732 \
  scripts/e2e/dev-instance.sh up native
node run.mjs --mode=native --instance-root=/tmp/rast-native-e2e --scenario=all
node perf/run-perf.mjs --mode=native --instance-root=/tmp/rast-native-e2e

# comparison table
node perf/run-perf.mjs --compare
```
